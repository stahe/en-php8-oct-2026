    We are now going to discover how to structure a PHP application in layers:

    In this diagram, it is the left-hand layer that takes the initiative of using the right-hand layer. The role of the layers is as follows:

    • [1]: the layer called [dao] (Data Access Objects) handles exchanges with external data stores [4] (files, databases, web services…). This layer is sometimes called [DAL] (Data Access Layer), a term that better describes its role. This layer can read data [3] or write data [2]. It is called upon by the [métier] layer [6] and returns results to it [7];
    • [5]: a layer called [métier] (business) that groups together "business" procedures to which all the data they need is supplied. It is generally the most stable layer of a project because it does not depend on the way the data are acquired. The data have two sources:
      • [9]: the data supplied by the PHP script;
      • [6, 7]: the data requested from the [dao] layer;
    • [8]: the main script is the conductor. In a console application, it will:
      • create the [métier] and [dao] layers;
      • run the application's algorithm. This algorithm is that of a conductor: it contains no "business" or data-access code. The main script merely calls the procedures of the [métier] layer [9]. It knows nothing at all about the [dao] layer and the external data. It can supply data to the [métier] layer [9]. In a console application, these data may come from configuration files or from the user of the script. It receives results [10] from the [métier] layer. It may need to store some results: to do so it again uses the procedures of the [métier] layer, which in turn will address the [dao] layer, which will do the work;
      • among the results, the main script may receive exceptions. It is its role to handle the exceptions that propagate up from all the layers.

    This layering is intended to make the application easier to evolve. To this end, each layer implements an interface. Suppose that:

    • the [dao] layer is implemented by a [Dao] class that implements an [IDao] interface;
    • the [métier] layer is implemented by a [Metier] class that implements an [IMetier] interface.

    The procedures of the [métier] layer will then use the [IDao] interface rather than the [Dao] class. This makes it possible to evolve the [dao] layer without touching the [métier] layer. Suppose that in a version 1, the [Dao1] layer uses data from a database. Following a change, these data are now supplied by a web service in a version 2, [Dao2]. We will make sure that both classes [Dao1] and [Dao2] implement the same [IDao] interface and that they throw the same exceptions. If this holds, the [Metier] layer, which works with the [IDao] interface, will remain unchanged.

    The same reasoning applies to the [métier] layer.

    10.4. The [métier] layer

    The [métier] layer offers the following [IMetier] interface [IMetier.php]:

    <?php

declare(strict_types=1);

// couche [métier] ------------------------
interface IMetier extends IDao
{
    // on exploite une personne
    public function doSomething(Personne $p): void;
}

    Comments

    • line 6: the [IMetier] interface extends the [IDao] interface. This is not at all mandatory. We do it here because the example is simple: the [métier] layer offers the main script the [get] and [save] methods of the [dao] layer, which it hides from it;
    • line 9: the [doSomething] method is specific to the [métier] layer.

    The PHP 7 course named the interface [IMétier] and the class [Métier], with an accent. PHP accepts accented letters in identifiers, but a file named [Métier.php] causes problems with some tools (zip archives, file systems, class autoloading). From now on we stick to class and file names without accents.

    <?php

declare(strict_types=1);

final class Metier implements IMetier
{
    // la couche [dao] est injectée par le constructeur
    public function __construct(private readonly IDao $dao)
    {
    }

    // on exploite une personne
    #[\Override]
    public function doSomething(Personne $p): void
    {
        // traitement
        print "[Métier] : Traitement métier de la personne $p\n";
    }

    // sauvegarde de la personne
    #[\Override]
    public function save(Personne $p): void
    {
        print "[Métier] : Sauvegarde de la personne $p\n";
        // on demande à la couche [dao] de faire la sauvegarde
        $this->dao->save($p);
    }

    // récupération d'une personne
    #[\Override]
    public function get(int $id): Personne
    {
        print "[Métier] : Récupération de la personne d'identifiant $id\n";
        // on demande la personne à la couche [dao]
        return $this->dao->get($id);
    }
}

    Comments

    • line 8: the [métier] layer must have a reference to the [dao] layer in order to use its methods. This reference is passed to it through its constructor and stored in the private read-only property [$dao] (parameter promotion). Note that the type of the parameter is the [IDao] interface. Thus the [métier] layer will be able to work with any class implementing the [IDao] interface. If we switch from a [Dao1] layer to a [Dao2] layer and both implement the [IDao] interface, the [métier] layer does not have to be rewritten;
    • this technique is called constructor dependency injection: the [Metier] class does not itself create the [dao] layer it depends on; it is supplied with it. The PHP 7 course used a [setDao] setter. Constructor injection is the rule today: a [Metier] object cannot exist without its [dao] layer, and the latter can no longer be changed afterwards ([readonly] property). This is also what PHP frameworks such as Symfony or Laravel do;
    • lines 14-18: implementation of [IMetier::doSomething];
    • lines 22-27: implementation of [IMetier::save]. This method must save a person in a data store. The [métier] layer does not know how to do that. It addresses the [dao] layer to perform this save (line 26);
    • lines 31-36: implementation of [IMetier::get]. This method must retrieve from a data store the person whose identifier is passed to it as a parameter. The [métier] layer does not know how to do that. It addresses the [dao] layer to do the work (line 35).

    Conclusion: as soon as the [métier] layer needs to access the data stored in the data store, it must go through the [dao] layer, which was created to access these data.

    We are going to write two conductor scripts for this application. The 1st, [main1.php], will use the [Dao1] layer, while the second, [main2.php], will use the [Dao2] layer. We want to show that this has no impact on the code of the [Metier] layer.

// respect strict des types déclarés des paramètres et des résultats des fonctions
declare(strict_types=1);

// inclusion des classes et interfaces
require_once __DIR__ . "/Personne.php";
require_once __DIR__ . "/IDao.php";
require_once __DIR__ . "/IMetier.php";
require_once __DIR__ . "/Dao1.php";
require_once __DIR__ . "/Metier.php";

// création des couches : la couche [dao] est injectée dans la couche [métier]
$métier = new Metier(new Dao1());
// utilisation de la couche [métier]
$personne = $métier->get(4);
$métier->doSomething($personne);
$métier->save($personne);

    Comments

    • the [main1.php] script is the conductor of the application. It loads the files of the classes and interfaces (lines 7-11), creates the layered structure of the application (line 14) and then talks to the [métier] layer (lines 16-18);
    • line 14: it is here, and only here, that the implementation of the [dao] layer is chosen;
    • according to the diagram of the layered structure, the [main1.php] script must address only the [métier] layer. It must not address the [dao] layer, even though this is theoretically possible.
