    23. Practical Exercise – Version 12

    In this chapter, we will write a web application that follows the MVC architecture (Model-View-Controller). The application will be able to return responses in three formats: JSON, XML, and HTML. There is a significant increase in complexity between what we are about to do and what we have done previously. We will reuse most of the concepts covered so far and will detail all the steps leading to the final application.

    23.1. MVC Architecture

    We will implement the architecture model known as MVC (Model–View–Controller) as follows:

    The processing of a client request will proceed as follows:

    • 1 - Request: The requested URL parameters will be in the form [http://machine:port/contexte/main.php?action=uneAction&param1=v1&param2=v2&…]. The [Contrôleur principal] will use the [action] parameter from the URL to “route” the request to the secondary controller responsible for processing this action. The remainder of the URL and [param1=v1&param2=v2&…] consists of optional parameters that will be passed to the action. The C in MVC is the string [Contrôleur principal, Contrôleur / Action]. If no controller can process the requested action, the server will respond that the requested action is invalid;
    • 2 - Processing:
      • The selected action [2a] can use the parameters passed to it by [Contrôleur principal]. These parameters may come from several sources: the [/param1/param2/…] path from URL, the [param1=v1&param2=v2] parameters from URL, or parameters submitted by the browser with its request;
      • When processing the user’s request, the action may require the [métier] and [2b] layers. Once the client’s request has been processed, it may trigger various responses. A classic example is: an error response if the request could not be processed correctly, or a confirmation response otherwise;
      • [Contrôleur / Action] will return its response, [2c], to the main controller along with a status code. These status codes will uniquely represent the current state of the application. They will be either success codes or error codes;
    • 3 - Response:
      • Depending on whether the client requested a response of JSON, XML, or HTML, the [Contrôleur principal] will instantiate the appropriate response type ([3a]) and instruct it to send the response to the client. The [Contrôleur principal] will pass it the response and status code provided by the [Contrôleur / Action] that was executed;
      • if the desired response is of type JSON or XML, the selected response will format the response from [Contrôleur / Action] that was provided to it and send it via [3c]. The client capable of processing this response can be a PHP console script or a JavaScript script embedded in a HTML page;
      • if the desired response is of type HTML, the selected response will choose one of the views [3b], HTML, or [Vuei] using the status code provided to it. This is the V for MVC. Each status code corresponds to a single view. This view V will display the response from the executed [Contrôleur / Action]. It formats the data from this response using HTML, CSS, and JavaScript. This data is called the view model. It is the “M” in MVC. The client is most often a web browser.

    Now, let’s clarify the relationship between web architecture MVC and layered architecture. Depending on how the model is defined, these two concepts may or may not be related. Let’s consider a single-layer web application MVC:

    In the example above, each [Contrôleur / Action] component incorporates parts of the [métier] and [dao] layers. The [web] layer does indeed have a MVC architecture, but the application as a whole does not have a layered architecture. Here, there is only one layer that does everything.

    Now, let’s consider a multi-layer web architecture:

    The [web] layer can be implemented without following the MVC model. We then have a multi-layer architecture, but the web layer does not implement the MVC model.

    For example, in the .NET world, the [web] layercan be implemented using ASP.NET Core MVC, resulting in a layered architecture with a [web] layer of type MVC. Once this is done, we can replace this ASP.NET Core MVC layer with a ASP.NET Core [Razor Pages] layer while keeping the rest (business logic, DAO, driver) unchanged. We then have a layered architecture with a [web] layer that is no longer of type MVC.

    In MVC, we stated that model M is that of view V, c.-à-d—the set of data displayed by view V. Another definition of model M for MVC is given:

    Many authors consider that what is to the right of layer [web] forms the M model of MVC. To avoid ambiguity, we can refer to:

    • the domain model when referring to everything to the right of the layer [web];
    • the view model when referring to the data displayed by a view V.

    Using this directory structure, we can describe the flow of processing for an action requested by a client:

    • [main.php] receives the request;
    • after performing some preliminary checks (is the action one of the accepted actions?), it forwards the request to the secondary controller responsible for processing that action;
    • the secondary controller performs its tasks. In carrying out this task, it may need the layers [métier] and [dao], as well as the entities in the folder [Entities]. It returns its response to the primary controller [main.php], which activated it;
    • depending on the type of response [JSON, XML, HTML] requested by the client, the main controller [main.php] activates one of the responses from the folder [Responses];
    • The responses [JsonResponse, XmlResponse] send the response JSON or XML to the client, respectively;
    • The response [HtmlResponse] uses one of the views from the folder [Views] to send a response HTML to the client;
    • the various components access the [Logger] class in version 9 to write logs to the [Data/logs.txt] file. The following are logged:
      • the requested action;
      • the response from its controller. This is recorded in the JSON format regardless of the requested [JSON, XML, HTML] type;
    • in the event of a fatal error (status HTTP 500 Internal Server Error), the main controller [main.php] sends an email to the administrator using the [SendAdminMail] class from version 9.

// actions accepted by the application: the value for a case is the name of the action in the URL
enum Action: string
{
    case InitSession = "init-session";
    case AuthentifierUtilisateur = "authentifier-utilisateur";
    case CalculerImpot = "calculer-impot";
    case ListerSimulations = "lister-simulations";
    case SupprimerSimulation = "supprimer-simulation";
    case FinSession = "fin-session";
    case AfficherCalculImpot = "afficher-calcul-impot";

     // Does the action require the session type (json, xml, html) to be known?
    public function exigeTypeSession(): bool
    {
        return $this !== self::InitSession;
    }

     // Does the action require the user to be authenticated?
    public function exigeAuthentification(): bool
    {
        return match ($this) {
            self::InitSession, self::AuthentifierUtilisateur => false,
            default => true,
        };
    }
}

    23.5. Tools and Libraries

    23.5.1. The [curl] tool

    Course PHP 7 used the graphical tool [Postman] to query the various URL components of the web application. We use the command-line tool [curl], introduced in the chapter on web services. It allows us to:

    • use any URL: these are created manually;
    • to query the web server using a GET, POST, PUT, OPTIONS… (options [-X] and [-d]);
    • specify the parameters for GET (in URL) or POST (options [-d] and [--data-urlencode]);
    • set the HTTP headers for the request (option [-H]);
    • to receive a response in the JSON, XML, or HTML format;
    • to have access to the HTTP headers of the response (option [-i]);
    • to handle the session cookie like a browser: the [-c cookies.txt] option saves the cookies sent by the server to the [cookies.txt] file, while the [-b cookies.txt] option sends them back to the server.

    Since we manually generate the requested URL files, we’ll be able to test all possible error scenarios and see how the server responds. Remember that in a [PowerShell] terminal, you must type [curl.exe] instead of [curl]. All commands in this chapter are entered in a terminal opened in any working directory, where [curl] creates the file [cookies.txt].

    To post a parameter whose name contains accented characters, such as [marié], we’ll use the option [--data-urlencode "marié=oui"], which encodes the parameter’s name and value ([mari%C3%A9=oui]). In URL, we’ll write the encoded name ourselves: [num%C3%A9ro] for [numéro].

    23.5.2. The Symfony / Serializer Library

    Course PHP 7 used the [Symfony / Serializer] library to serialize server responses into JSON and XML, which may contain [Simulation] objects. It had two advantages: the same API for both JSON and XML; the serialization of objects with private attributes, exposed via getters.

    We do not use it in this version, although it is installed in the [vendor] folder for the course:

    • our class [Simulation] is a [readonly] class with public attributes (see the following paragraph). The function [json_encode] directly serializes an object’s public attributes: the JSON serialization no longer requires a library;
    • for XML, we have the [XmlUtilitaires] class from version 11, which produces XML documents in the same format as those from version 11, which XML clients already know how to process. All you need to do is provide it with an array, after converting the [Simulation] objects into associative arrays;
    • the server never has to deserialize JSON or XML into objects, which was the other advantage highlighted by the PHP 7 course.

    The [Symfony / Serializer] library would therefore only add one more dependency here. It remains a good choice when you need to deserialize documents into typed objects or handle many different formats.

    23.9.1. Introduction

    The main controller [main.php] is configured by the file [Data/config.json]. Let’s review its position in our MVC architecture:

    The main controller [main.php] is the first element in the MVC architecture to process the client’s request. It has several roles:

    • First, it performs basic checks:
      • Does its configuration file exist and is it valid?
      • it loads all the project dependencies. This involves loading all components of the MVC architecture;
      • Has the requested action been specified? If so, is it valid?

    • it retrieves [2c] the response from the secondary controller.     All secondary controllers proceed in the same way:

    • they check their parameters. These are found in the [$request->query] object for parameters present in the URL object and in the [$request->request] object for those that are posted (request POST);
    • A controller is similar to a function or method that checks the validity of its parameters. For the controller, however, it’s a bit more complicated:
      • the expected parameters may be missing;
      • the expected parameters are all character strings, whereas a function can specify the type of its parameters. If the expected parameter is a number, then you must verify that the parameter’s string actually represents a number;
      • once it has been verified that the expected parameters are present and syntactically correct, you must verify that they are valid within the current execution context. This context is stored in the session. Authentication is an example of an execution context: certain actions should only be processed once the client has been authenticated. A key in the session indicates whether this authentication has taken place or not;
    • Once the previous checks have been completed, the secondary controller can begin processing. This parameter validation is very important. We cannot allow a client to send us just anything at any point during the application’s lifecycle. We must maintain complete control over the application’s lifecycle;
    • Once its work is done, the secondary controller returns the [ControllerResult] object expected by the primary controller that called it.

     #[\Override]
    public function send(
        Request $request,
        Session $session,
        array $config,
        int $statusCode,
        array $content,
        array $headers = [],
        ?Logger $logger = null
    ): void {
         // The response HTML depends on the status code returned by the controller
        $état = $content["état"];
         // Each status corresponds to a view: we look for the first view whose status list contains [$état]
         // If no view matches, it is an unexpected error: the error view is displayed
        $vue = array_find_key(
            $config["vues"],
            fn(array $états): bool => in_array($état, $états, true)
        ) ?? $config["vue-erreurs"];
         // The view is executed: what it outputs is placed in a buffer instead of being sent to the client
         // The view has access to the method’s variables [$request, $session, $config, $content]
        ob_start();
        require __DIR__ . "/../Views/$vue";
         // The contents of the buffer—the document HTML—are retrieved, and the buffer is cleared
        $html = ob_get_clean();
         // the parent class sends the response
        $this->sendResponse($statusCode, $html, "text/html", $headers);
         // Log the controller’s response in JSON, excluding HTML
        $this->log($logger, $content);
    }
}

    23.13.5. Viewing Unexpected Errors

    Here, an unexpected error is defined as an error that should not have occurred during normal use of the web application. Let’s take the following request as an example, in session JSON:

    1
2
    > curl -c cookies.txt -b cookies.txt "http://localhost/php8-oct-2026/scripts-web/impots/version-12/main.php?action=calculer-impot" -d "salaire=y"
{"action":"calculer-impot","état":337,"réponse":["paramètre [marié] manquant","paramètre [enfants] manquant","valeur [y] invalide pour le paramètre [salaire]"]}

    The parameters [marié] and [enfants] are missing, and the parameter [salaire] is invalid. However, in the HTML form of the web application, this situation cannot occur:

    • all parameters are present;
    • the parameter [marié], which derives its value from the [value] attributes of two radio buttons, must be either [oui] or [non];
    • with a modern browser, the [<input type="number" min="0" step="1" …>] attributes ensure that the entries for children and salary are necessarily integers >= 0.

    However, nothing prevents a user from sending such a request to our server—using [curl] or their browser’s developer tools—during a HTML session. We’ll call an “unexpected error” any error that shouldn’t occur within the HTML application. If it does occur, it’s likely because someone is trying to “hack” the application. For educational purposes, we’ve decided to display an error page for these cases. In reality, we could re-display the last page sent to the client. To do this, we simply need to store the last HTML response sent in the session. In the event of an unexpected error, we return this response. This way, the user will have the impression that the server is not responding to their errors since the displayed page does not change.

class ClientMetier implements InterfaceClientMetier

     // The [dao] layer is injected by the constructor
    public function __construct(private readonly InterfaceClientDao $clientDao)

     // Tax calculation in batch mode
     #[\Override]
    public function executeBatchImpots(
        string $taxPayersFileName,
        string $errorsFileName,
        ?string $resultsFileName = null
    ): void {
         // Exceptions originating from the [dao] layer are allowed to propagate
         // retrieve taxpayer data
        $taxPayersData = $this->clientDao->getTaxPayersData($taxPayersFileName, $errorsFileName);
         // Calculate the tax for each taxpayer: the server stores the simulations in the session

            fn(TaxPayerData $taxPayerData): Simulation => $this->calculerImpot(
                $taxPayerData->marié,
                $taxPayerData->enfants,
                $taxPayerData->salaire
            ),
            $taxPayersData
        );
         // Save the results, if requested
        if ($resultsFileName !== null) {
            $this->clientDao->saveResults($resultsFileName, $simulations);
        }
    }

     // other methods delegate the work to the [dao] layer
     #[\Override]
    public function calculerImpot(string $marié, int $enfants, int $salaire): Simulation
    {
        return $this->clientDao->calculerImpot($marié, $enfants, $salaire);
    }

    public function saveResults(string $resultsFilename, array $simulations): void
    {
        $this->clientDao->saveResults($resultsFilename, $simulations);
    }

    public function initSession(string $type = "json"): void
    {
        $this->clientDao->initSession($type);
    }

     #[\Override]
    public function authentifierUtilisateur(string $user, #[\SensitiveParameter] string $password): void
    {
        $this->clientDao->authentifierUtilisateur($user, $password);
    }

    {

    }

    {

    }

namespace Application\Tests;

use Application\ClientDao;

use Application\ExceptionImpots;
use Application\InterfaceClientMetier;

use PHPUnit\Framework\Attributes\DataProvider;

// Testing the [métier] layer of the JSON web service client: the server must be running
final class ClientMetierTest extends TestCase
{
     // the client's root directory
    private const string ROOT_DIRECTORY = __DIR__ . "/..";
     // client configuration
    private static array $config;
     // The [métier] layer tested
    private InterfaceClientMetier $métier;

     // run once, before the first test in the class
     #[\Override]
    public static function setUpBeforeClass(): void
    {
         // retrieving the client configuration
        self::$config = json_decode(file_get_contents(self::ROOT_DIRECTORY . "/Data/config.json"), true, flags: JSON_THROW_ON_ERROR);
         // includes client dependencies (the Composer loader is already loaded by PHPUnit)
        foreach (self::$config["dependencies"] as $dependency) {
            require_once self::ROOT_DIRECTORY . "/$dependency";
        }
    }

     // run before each test: each test has its own authenticated JSON session
     #[\Override]
    protected function setUp(): void
    {
         // creation of layers [dao] (non-verbose) and [métier]
        $clientDao = new ClientDao(self::$config["urlServer"], self::$config["httpClientOptions"], verbose: false);
        $this->métier = new ClientMetier($clientDao);
         // initializing a session JSON
        $this->métier->initSession("json");
         // authentication
        $this->métier->authentifierUtilisateur(self::$config["user"]["login"], self::$config["user"]["passwd"]);
    }

     // Taxpayers in the table of official figures
    public static function contribuables(): array
    {

     // a test run once for each taxpayer of the data provider
     #[DataProvider("contribuables")]
    public function testCalculerImpot(string $marié, int $enfants, int $salaire, int $impôtOfficiel, array $attendu): void
    {
         // tax calculation
        $simulation = $this->métier->calculerImpot($marié, $enfants, $salaire);
         // The tax amount matches that of the official simulator to within 1 euro
        $this->assertEqualsWithDelta($impôtOfficiel, $simulation->impôt, 1);
         // The simulation is exactly as expected: [assertEquals] compares the attributes of the two objects
        $this->assertEquals(new Simulation($marié, $enfants, $salaire, ...$attendu), $simulation);
    }

     // the actions [lister-simulations] and [supprimer-simulation]
    public function testListerSupprimerSimulations(): void
    {
         // two simulations in a new session
        $this->métier->calculerImpot("oui", 2, 55555);
        $this->métier->calculerImpot("non", 0, 100000);
        $this->assertCount(2, $this->métier->listerSimulations());
         // the first one was deleted: the second one remains
        $simulations = $this->métier->supprimerSimulation(0);
        $this->assertCount(1, $simulations);
        $this->assertSame(22986, $simulations[0]->impôt);
         // Simulation #1 no longer exists: status 628, status HTTP 400
        $this->assertErreur(400, 628, fn() => $this->métier->supprimerSimulation(1));
    }

     // After the session ends, the user is no longer authenticated
    public function testFinSession(): void
    {
        $this->métier->finSession();
         // status 104: action requested by an unauthenticated user
        $this->assertErreur(400, 104, fn() => $this->métier->listerSimulations());
    }

     // Verifies that the action [$action] throws an exception [ExceptionImpots] with code 42
     // whose message JSON contains the expected status HTTP
    private function assertErreur(int $statutHttp, int $état, \Closure $action): void
    {
        try {
            $action();
            $this->fail("une exception [ExceptionImpots] était attendue");
        } catch (ExceptionImpots $ex) {
            $this->assertSame(42, $ex->getCode());
            $erreur = json_decode($ex->getMessage(), true, flags: JSON_THROW_ON_ERROR);
            $this->assertSame($statutHttp, $erreur["statut HTTP"]);
            $this->assertSame($état, $erreur["état"]);
        }
    }
}

    • lines 31–37: The client configuration is read and dependencies are loaded only once, before the first test;
    • Lines 43–51: Note that the [setUp] method is executed before each test. It constructs the layers [dao] (in non-verbose mode) and [métier], then initializes a session JSON and authenticates itself. Each test thus runs in its own session, independent of the other tests. Course PHP 7 performed this task in the test class constructor, which PHPUnit no longer allows;
    • lines 55–69: the data provider from previous versions. For each taxpayer, we have the tax calculated by the official simulator and the five expected results from [impôt, surcôte, décôte, réduction, taux];
    • line 82: the expected simulation is constructed and compared to the one returned by the server. When applied to two objects, the [assertEquals] method verifies that they are of the same class and that their attributes are equal. The operator [...] decomposes a list here: its elements are passed to the last five parameters of the constructor, in order;
    • Lines 86–97: A test of the actions [lister-simulations] and [supprimer-simulation]. We run two simulations, delete the first one, and verify that the second one remains. Then we request the deletion of a simulation that does not exist: the server must respond with status 628;
    • lines 101–105: After the session ends, the list of simulations must be rejected with status code 104;
    • lines 110–119: a utility method that verifies that the action [$action], passed as an anonymous function, throws a [ExceptionImpots] exception with code 42, the expected status HTTP, and the expected status. Since the exception message is the server’s JSON response, it is decoded to verify its elements. If no exception is thrown, the [fail] method causes the test to fail.
