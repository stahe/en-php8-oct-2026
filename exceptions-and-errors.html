    7. Exceptions and errors

    When a method of a class encounters an unrecoverable error (non-existent file, database not connected, network connection down), it does not display an error on a console (file, database) but throws an exception. Exceptions extend the [\Exception] class. Besides exceptions, PHP's internal machinery also throws errors whose base class is the [\Error] class. Both classes implement the PHP interface [\Throwable].

    PHP 8 profoundly changed error handling: many situations that in PHP 7 produced a mere warning (and an often absurd result) now throw an error that can be caught. We will see this throughout the examples.

    7.2. The [\Throwable] interface

    The [\Throwable] interface is as follows (see the documentation):

    interface Throwable extends Stringable
{
    public function getMessage(): string;
    public function getCode(): int;
    public function getFile(): string;
    public function getLine(): int;
    public function getTrace(): array;
    public function getTraceAsString(): string;
    public function getPrevious(): ?Throwable;
    public function __toString(): string;
}

    The role of the interface's methods is as follows:

    Method
    Role
    [getMessage]
    returns the error message
    [getCode]
    returns the error code (an integer)
    [getFile]
    returns the name of the file where the object was created
    [getLine]
    returns the number of the line where the object was created
    [getTrace]
    returns the function call stack as an array
    [getTraceAsString]
    returns the function call stack as a string
    [getPrevious]
    returns the previous (wrapped) [Throwable] object, or [null]
    [__toString]
    returns a string representation of the object

    Note that the [Throwable] interface extends the [Stringable] interface encountered in the chapter on classes. A class cannot implement the [Throwable] interface directly: it must derive from [\Exception] or from [\Error].

    <?php

// respect strict des types déclarés des paramètres de fonctions
declare(strict_types=1);

// affiche l'arborescence des classes prédéfinies implémentant l'interface [Throwable]
// on se limite aux extensions toujours présentes dans PHP 8.5 :
// le noyau (Core), la bibliothèque standard, la bibliothèque SPL, jSON et Random
$extensions = ["Core", "standard", "SPL", "json", "random"];

// les classes prédéfinies de ces extensions qui implémentent [Throwable]
$classes = array_filter(
    get_declared_classes(),
    function (string $classe) use ($extensions): bool {
        $reflexion = new ReflectionClass($classe);
        return $reflexion->isInternal()
            && $reflexion->implementsInterface(Throwable::class)
            && in_array($reflexion->getExtensionName(), $extensions, true);
    }
);
sort($classes);

// affichage récursif des classes filles de la classe [$parent]
function afficher(?string $parent, array $classes, string $indentation): void
{
    // les filles directes de [$parent]
    $filles = array_values(array_filter(
        $classes,
        fn(string $classe): bool => (get_parent_class($classe) ?: null) === $parent
    ));
    foreach ($filles as $i => $fille) {
        $derniere = $i === count($filles) - 1;
        print $indentation . ($derniere ? "└── " : "├── ") . $fille . "\n";
        afficher($fille, $classes, $indentation . ($derniere ? "    " : "│   "));
    }
}

print "Throwable\n";
afficher(null, $classes, "");

    • line 13: the [get_declared_classes] function returns the list of all classes known at that moment, predefined or not;
    • lines 16-18: we keep only the predefined (internal) classes that implement the [Throwable] interface and belong to the extensions always present in PHP 8.5 (line 9). Other extensions add their own exceptions (for example [PDOException] for database access, which we will meet later);
    • lines 24-36: a recursive function that displays the direct child classes of the [$parent] class, then the children of each of them, and so on. The [get_parent_class] function returns [false] for a class without a parent: the [?:] operator then turns [false] into [null];
    • line 29: an arrow function (PHP 7.4), a short form of an anonymous function reduced to a single expression;
    • line 39: we start from the classes without a parent: [Error] and [Exception].

    The results show two families:

    • the [Exception] family: these are the exceptions thrown by libraries and application code. It includes:
      • [ErrorException], which lets you turn a PHP warning into an exception (we will use it at the end of the chapter);
      • [JsonException] (PHP 7.3), thrown by [json_encode] and [json_decode] with the [JSON_THROW_ON_ERROR] option;
      • [Random\RandomException] (PHP 8.2), thrown by the random number generation functions;
      • the exceptions of the SPL (Standard PHP Library), a collection of classes and interfaces intended to solve problems frequently encountered by developers. They form two sub-families:
      • [LogicException] and its subclasses: programming errors, which a fix of the code should make disappear: invalid argument ([InvalidArgumentException]), value outside the expected domain ([DomainException]), non-existent method ([BadMethodCallException])...;
      • [RuntimeException] and its subclasses: errors that can only be detected at runtime: index out of bounds ([OutOfBoundsException]), unexpected value ([UnexpectedValueException]), capacity overflow ([OverflowException])...;
    • the [Error] family: these are the errors thrown by the PHP engine itself. It includes:
      • [TypeError]: a value does not have the expected type (function parameter, typed property, return value, operand of an operator...). Its subclass [ArgumentCountError] reports too few arguments;
      • [ValueError] (PHP 8.0): a value has the right type but an invalid value (for example a negative or zero length);
      • [ArithmeticError] and its subclass [DivisionByZeroError]: errors in arithmetic operations;
      • [UnhandledMatchError] (PHP 8.0): no arm of a [match] expression matches;
      • [AssertionError]: failure of an [assert] assertion;
      • [CompileError] and its subclass [ParseError]: syntax error in a file loaded by [require] or [include];
      • [FiberError] (PHP 8.1) and [Random\RandomError] (PHP 8.2): errors related to fibers and random generators, which we will not use.

    The two families are not related in any way: a [catch (\Exception $e)] clause does not catch an [Error]. Only the [Throwable] interface brings them together.

// respect strict des types déclarés des paramètres de fonctions
declare(strict_types=1);

// on affiche toutes les erreurs
error_reporting(E_ALL);
ini_set("display_errors", "1");
// on entoure le code par un try / catch
try {
    $var = [];
    // clé inconnue
    print $var["abcd"];
    // division par zéro
    $var = 7 / 0;
    var_dump($var);
    // tableau à bornes fixes
    $array = new \SplFixedArray(5);
    $array[1] = 2;
    $array[4] = "foo";
    // indice en-dehors des bornes
    $array[5] = 8;
    // vérification
    print "ce message ne sera pas affiché\n";
} catch (\Throwable $ex) {
    // \Throwable est l'interface implémentée par toutes les erreurs et exceptions
    // on affiche l'exception
    print "erreur, message : " . $ex->getMessage() . ", type : " . $ex::class . "\n";
}

    Comments

    • the script is the one presented in the previous section. Only now, we have surrounded the code likely to cause errors with a [try / catch] structure: if the code of lines 11-24 causes (throws) an exception or an error, it will be handled by the [catch] clause of lines 25-29;
    • line 25: the parameter of the [catch] clause is the type of exception or error we want to handle. By using as type [\Throwable], which is an interface, we indicate that we want to handle any instance of a class implementing the [\Throwable] interface. Since all error and exception classes implement this interface, the [catch] clause here handles any error / exception;
    • line 15: the statement that triggers the error. As soon as an exception occurs, execution branches to the [catch] clause. The code that follows in the [try] is therefore not executed;
    • line 28: the notation [$ex::class] returns the name of the class of the [$ex] object.

    7.7. The [finally] clause

    The [try / catch] structure can have a third element and become a [try / catch / finally] structure. The code of the [finally] clause is executed in the following two cases:

    • the [try] clause does not throw an exception. It is then executed in full, then execution moves on to the [finally] clause, which is executed in full;
    • the [try] clause throws an exception. It is then executed up to the statement that throws the exception. Execution then moves on to the [catch] clause, which is executed in full. Then execution moves on to the [finally] clause, which is executed in full.

    Ultimately, the code of the [finally] clause is always executed. This scenario is useful in the following case:

    • in the [try], the code has obtained resources (files, databases, network connections, queues). These resources are generally costly. They must then be released (most often we say closed) as soon as possible;
    • if the resources were acquired in the [try], their release will be placed in the [finally]. This ensures that in every case (error or not), the acquired resources are returned to the system.

    7.8. Creating your own exception classes

    In a project of some size, it is useful to distinguish the various errors by wrapping them in different exception classes. In the previous scripts, we saw that any exception could be caught by a [catch (\Throwable $ex)] clause. restore_error_handler();
print "fin\n";

    This technique is used by many PHP frameworks (Symfony, Laravel): in development, any warning becomes an exception, which forces you to fix the code. The [PHPUnit] testing tool that we will use later proceeds in a similar way: it can make a test fail if it produces a warning or a deprecation.
