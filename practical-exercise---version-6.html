    14.1. Installing the PostgreSQL DBMS

    The PHP 7 course downloaded the PostgreSQL installer for Windows from the site [https://www.postgresql.org/download/], ran it, then changed the PostgreSQL Windows service, which started automatically when the machine booted, into a manually started service. With [Laragon], none of this is necessary: PostgreSQL is one of the services managed by [Laragon], just like Apache and MySQL. It is started and stopped from the [Laragon] menu (PostgreSQL menu), and it runs only when we need it. Like MySQL, it listens on the local machine, on port 5432, its default port.

    Like MySQL, PostgreSQL has an administrator, the superuser [postgres]. In the [Laragon] installation, it has no password. If it has been given a password, the tools will ask for it.

    The [Laragon] terminal gives access to PostgreSQL's command-line client, [psql], the equivalent of the [mysql] client. The PostgreSQL documentation is available at [https://www.postgresql.org/docs/].

    14.2. Enabling the PostgreSQL PDO extension

    The PostgreSQL PDO driver is PHP's [pdo_pgsql] extension. We enable it as we did for the MySQL driver:

    • either from the [Laragon] menu: PHP / Extensions / pdo_pgsql;
    • or by checking that the following line is not commented out (no semicolon at the start of the line) in the [php.ini] file ([Laragon] menu PHP / php.ini):
    1
    extension=pdo_pgsql

    After saving the change, we restart the [Laragon] services ([Reload] button). We then check that the driver is present with the [pdo-drivers.php] script from the chapter on MySQL, run in the [scripts-console/mysql] folder:

    Comments

    • lines 7-8: we delete the database and the user if they exist, so that the script can be rerun. With PostgreSQL, a name containing a hyphen is surrounded by double quotes, and not by backquotes as with MySQL: this is a first difference between the two DBMSs;
    • line 9: PostgreSQL calls its users "roles". The [LOGIN] attribute allows the role [admimpots] to connect to the DBMS;
    • line 10: creation of the [dbimpots-2019] database. Its owner is [admimpots], which gives it all privileges on the database. The character encoding is UTF-8. The database is built from the template database [template0], which accepts any encoding;
    • line 13: this line is not an SQL statement but a command of the [psql] client (it begins with a backslash). It connects the client to the [dbimpots-2019] database that has just been created. With PostgreSQL, there is no equivalent of MySQL's [USE] statement: a connection works on a single database;
    • line 16: the following statements are executed as [admimpots], who will thus be the owner of the tables created;
    • lines 19-25: the [tbtranches] table. The primary key [id] is of type [INTEGER GENERATED ALWAYS AS IDENTITY]: the DBMS generates its values at insertion time, as MySQL's [AUTO_INCREMENT] attribute did. This syntax is that of the SQL standard; [AUTO_INCREMENT] is MySQL-specific. The [NUMERIC] type is the equivalent of MySQL's [DECIMAL] type;
    • lines 28-41: the [tbconstantes] table. The column names are written in lowercase, with words separated by underscores (plafond_qf_demi_part).

    Why these column names? A peculiarity of PostgreSQL is that column names can be case-sensitive (uppercase / lowercase), which is not usually the case with other DBMSs. Thus with MySQL, the statement [select limites, coeffR, coeffN from tbtranches] works even if the actual columns of the [tbtranches] table are [LIMITES, COEFFR, COEFFN]. With PostgreSQL, it does not work, because PostgreSQL converts names that are not surrounded by double quotes to lowercase: it actually executes the statement [select limites, coeffr, coeffn from tbtranches]. To prevent it from doing so, you must write [select "LIMITES", "COEFFR", "COEFFN" from tbtranches], that is, protect the column names with double quotes. For these reasons, we give the columns lowercase names, and we cannot reuse the camelCase names (plafondQfDemiPart) of the MySQL database. The names of database objects can be a source of incompatibility between DBMSs, some names being reserved words in some DBMSs and not in others.
