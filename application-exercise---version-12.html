    23. Application exercise – version 12

    In this chapter we will write a web application that follows the MVC (Model-View-Controller) architecture. The application will be able to deliver its responses in three formats: JSON, XML, HTML. There is a jump in complexity between what we are about to do now and what has been done previously. We will reuse most of the concepts seen so far and we will detail all the steps leading to the final application.

    23.1. MVC architecture

    We will implement the so-called MVC (Model – View – Controller) architectural pattern as follows:

    The processing of a client request will proceed as follows:

    • 1 - request: the requested URLs will be of the form [http://machine:port/contexte/main.php?action=uneAction&param1=v1&param2=v2&…]. The [Main controller] will use the [action] parameter of the URL to "route" the request to the secondary controller responsible for processing this action. The rest of the URL [param1=v1&param2=v2&…] consists of optional parameters that will be passed to the action. The C of MVC is here the chain [Main controller, Controller / Action]. If no controller can process the requested action, the server will respond that the requested action is invalid;
    • 2 - processing:
      • the chosen action [2a] can use the parameters that the [Main controller] has passed to it. These can come from several sources: the path [/param1/param2/…] of the URL, the parameters [param1=v1&param2=v2] of the URL, parameters posted by the browser with its request;
      • while processing the user's request, the action may need the [métier] layer [2b]. Once the client's request has been processed, it can call for various responses. A classic example is: an error response if the request could not be processed correctly, a confirmation response otherwise;
      • the [Controller / Action] will return its response [2c] to the main controller along with a state code. These state codes will uniquely represent the state the application is in. They will be either success codes or error codes;
    • 3 - response:
      • depending on whether the client has requested a JSON, XML or HTML response, the [Main controller] will instantiate [3a] the appropriate response type and ask it to send the response to the client. The [Main controller] will pass it the response and the state code provided by the [Controller / Action] that was executed;
      • if the desired response is of type JSON or XML, the selected response will format the response of the [Controller / Action] it was given and send it [3c]. The client able to use this response can be a PHP console script or a JavaScript script hosted in an HTML page;
      • if the desired response is of type HTML, the selected response will choose [3b] one of the HTML views [Vuei] using the state code it was given. This is the V of MVC. A state code corresponds to a single view. This view V will display the response of the [Controller / Action] that was executed. It dresses the data of this response with HTML, CSS, JavaScript. This data is called the view model. This is the M of MVC. The client is then most often a browser.

    Now, let us clarify the link between the MVC web architecture and the layered architecture. Depending on the definition given to the model, these two concepts are related or not. Let us take a single-layer MVC web application:

    Above, the [Controller / Action] components each incorporate part of the [métier] and [dao] layers. In the [web] layer we do have an MVC architecture, but the application as a whole does not have a layered architecture. Here there is only one layer that does everything.

    Now, let us consider a multi-layer web architecture:

    The [web] layer can be implemented without following the MVC pattern. We then do have a multi-layer architecture, but the web layer does not implement the MVC pattern.

    For example, in the .NET world the [web] layer above can be implemented with ASP.NET Core MVC, and we then have a layered architecture with an MVC-type [web] layer. Once this is done, we can replace this ASP.NET Core MVC layer with an ASP.NET Core [Razor Pages] layer while keeping the rest (business, DAO, driver) identical. We then have a layered architecture with a [web] layer that is no longer of the MVC type.

    In MVC, we said that the model M was that of the view V, i.e. the set of data displayed by the view V. Another definition of the model M of MVC is given:

    Many authors consider that what lies to the right of the [web] layer forms the model M of MVC. To avoid ambiguity, we can speak of:

    • the domain model when referring to everything to the right of the [web] layer;
    • the view model when referring to the data displayed by a view V.

    Using this tree structure, we can describe the processing path of an action requested by a client:

    • [main.php] receives the request;
    • after performing a few preliminary checks (is the action one of the accepted actions?), it passes the request on to the secondary controller responsible for processing this action;
    • the secondary controller does what it has to do. In its work, it may need the [métier] and [dao] layers as well as the entities of the [Entities] folder. It returns its response to the main controller [main.php] that activated it;
    • depending on the response type [JSON, XML, HTML] desired by the client, the main controller [main.php] activates one of the responses of the [Responses] folder;
    • the responses [JsonResponse, XmlResponse] send the JSON or XML response respectively to the client;
    • the [HtmlResponse] response uses one of the views of the [Views] folder to send an HTML response to the client;
    • the various elements have access to the [Logger] class of version 9 to write logs to the file [Data/logs.txt]. The following are logged:
      • the requested action;
      • the response of its controller. It is recorded in JSON format regardless of the type [JSON, XML, HTML] requested;
    • in the event of a fatal error (HTTP status 500 Internal Server Error), the main controller [main.php] sends an email to the administrator using the [SendAdminMail] class of version 9.

declare(strict_types=1);

// espace de noms
namespace Application;

// les actions acceptées par l'application : la valeur d'un cas est le nom de l'action dans l'URL
enum Action: string
{
    case InitSession = "init-session";
    case AuthentifierUtilisateur = "authentifier-utilisateur";
    case CalculerImpot = "calculer-impot";
    case ListerSimulations = "lister-simulations";
    case SupprimerSimulation = "supprimer-simulation";
    case FinSession = "fin-session";
    case AfficherCalculImpot = "afficher-calcul-impot";

    // l'action exige-t-elle que le type de la session (json, xml, html) soit connu ?
    public function exigeTypeSession(): bool
    {
        return $this !== self::InitSession;
    }

    // l'action exige-t-elle que l'utilisateur soit authentifié ?
    public function exigeAuthentification(): bool
    {
        return match ($this) {
            self::InitSession, self::AuthentifierUtilisateur => false,
            default => true,
        };
    }
}

    23.5. Tools and libraries

    23.5.1. The [curl] tool

    The PHP 7 course used the graphical tool [Postman] to query the various URLs of the web application. We use the command-line tool [curl], presented in the chapter on web services. It allows us:

    • to use any URL: they are made by hand;
    • to query the web server with a GET, POST, PUT, OPTIONS… (options [-X] and [-d]);
    • to specify the parameters of the GET (in the URL) or of the POST (options [-d] and [--data-urlencode]);
    • to set the HTTP headers of the request (option [-H]);
    • to receive a response in JSON, XML, HTML format;
    • to have access to the HTTP headers of the response (option [-i]);
    • to manage the session cookie like a browser: the option [-c cookies.txt] saves in the file [cookies.txt] the cookies sent by the server, the option [-b cookies.txt] sends them back to the server.

    Since we make the queried URLs by hand, we will be able to test all the possible error cases and see how the server reacts. Remember that in a [PowerShell] terminal, you must type [curl.exe] rather than [curl]. All the commands of this chapter are typed in a terminal opened in any working folder, where [curl] creates the file [cookies.txt].

    To post a parameter whose name contains accented characters, such as [marié], we will use the option [--data-urlencode "marié=oui"], which encodes the name and the value of the parameter ([mari%C3%A9=oui]). In the URL, we will write the encoded name ourselves: [num%C3%A9ro] for [numéro].

    23.5.2. The Symfony / Serializer library

    The PHP 7 course used the [Symfony / Serializer] library to serialize into JSON and XML the server's responses, which may contain [Simulation] objects. It had two advantages: the same API for JSON and XML; the serialization of objects with private attributes, exposed through getters.

    We do not use it in this version, even though it is installed in the course's [vendor] folder:

    • our [Simulation] class is a [readonly] class with public attributes (see next section). The [json_encode] function directly serializes the public attributes of an object: JSON serialization no longer requires a library;
    • for XML, we have the [XmlUtilitaires] class of version 11, which produces XML documents of the same form as those of version 11, which the XML clients already know how to use. We just have to give it an array, after transforming the [Simulation] objects into associative arrays;
    • the server never has to deserialize JSON or XML into objects, which was the other advantage put forward by the PHP 7 course.

    The [Symfony / Serializer] library would therefore only add one more dependency here. It remains a good choice when documents must be deserialized into typed objects or when many formats must be handled.

    23.9.1. Introduction

    The main controller [main.php] is configured by the file [Data/config.json]. Let us recall its position in our MVC architecture:

    The main controller [main.php] is the 1st element of the MVC architecture to process the client's request. It has several roles:

    • it first performs the basic checks:
      • does its configuration file exist and is it valid?
      • it loads all the project's dependencies. This amounts to loading all the elements of the MVC architecture;
      • has the requested action been specified? If so, is it valid?
    • if the requested action is valid, it selects [2a] the secondary controller that will process it and passes it the information it needs: the application configuration, the HTTP request, the session;
    • it retrieves [2c] the secondary controller's response. Depending on the response type (JSON, XML, HTML) requested by the client, it selects [3a] the response (JsonResponse, XmlResponse, HtmlResponse) responsible for sending the response to the client and passes it all the information it needs (the HTTP request, the session, the application configuration, the secondary controller's response).

    All the secondary controllers proceed in the same way:

    • they check their parameters. These are found in the [$request->query] object for the parameters present in the URL and in the [$request->request] object for those that are posted (POST request);
    • a controller is similar to a function or method that checks the validity of its parameters. For the controller, however, it is a little more complicated:
      • the expected parameters may be missing;
      • the expected parameters are all character strings, whereas a function can set the type of its parameters. If the expected parameter is a number, then it must be checked that the parameter's string is indeed that of a number;
      • once it has been checked that the expected parameters are present and syntactically correct, it must be checked that they are valid in the current execution context. This context is present in the session. Authentication is an example of execution context: certain actions must only be processed once the client is authenticated. A key in the session indicates whether or not this authentication has taken place;
    • once the previous checks have been made, the secondary controller can do its work. This parameter-checking work is very important. We cannot accept that a client sends us anything at any moment in the life of the application. We must have full control over its life;
    • once its work is done, the secondary controller returns the [ControllerResult] object expected by the main controller that called it.

    {

        // réussite
        return new ControllerResult(Response::HTTP_OK, 700, "session démarrée avec type [$type]");

    public function execute(array $config, Request $request, Session $session): ControllerResult
    {
        // on doit avoir un POST avec le seul paramètre [action] dans l'URL
        if ($request->getMethod() !== "POST" || $request->query->count() !== 1) {
            $message = "méthode POST requise, paramètre [action] dans l'URL, paramètres postés [user, password]";
            return new ControllerResult(Response::HTTP_BAD_REQUEST, 201, $message);

        $état = 210;
        // user

            $état += 2;
            $erreurs[] = "paramètre [user] manquant";
        }
        // password
        if (!$request->request->has("password")) {
            $état += 4;
            $erreurs[] = "paramètre [password] manquant";
        }
        // erreurs ?
        if ($erreurs !== []) {
            return new ControllerResult(Response::HTTP_BAD_REQUEST, $état, $erreurs);
        }
        $user = trim($request->request->getString("user"));
        $password = trim($request->request->getString("password"));
        // l'utilisateur fait-il partie des utilisateurs autorisés ?
        $trouvé = array_any(
            $config["users"],
            fn(array $u): bool => $u["login"] === $user && hash_equals($u["passwd"], $password)
        );
        if (!$trouvé) {
            // échec : code 401 - le mot de passe n'est jamais renvoyé au client
            return new ControllerResult(Response::HTTP_UNAUTHORIZED, 221, "Echec de l'authentification [$user]");
        }
        // on note dans la session l'identifiant de l'utilisateur authentifié
        $session->set("user", $user);
        // réussite
        return new ControllerResult(Response::HTTP_OK, 200, "Authentification réussie [$user]");

// action [calculer-impot] : calcul de l'impôt avec les paramètres postés [marié, enfants, salaire]
final class CalculerImpotController implements InterfaceController
{
    #[\Override]
    public function execute(array $config, Request $request, Session $session): ControllerResult
    {
        // on doit avoir un POST avec le seul paramètre [action] dans l'URL
        if ($request->getMethod() !== "POST" || $request->query->count() !== 1) {
            $message = "il faut utiliser la méthode [post] avec [action] dans l'URL"
                . " et les paramètres postés [marié, enfants, salaire]";
            return new ControllerResult(Response::HTTP_BAD_REQUEST, 301, $message);
        }
        // on vérifie les paramètres postés
        // chaque erreur ajoute une valeur différente à l'état : l'état final dit quelles erreurs se sont produites
        $erreurs = [];
        $état = 310;
        // statut marital
        if (!$request->request->has("marié")) {
            $état += 2;
            $erreurs[] = "paramètre [marié] manquant";
        } else {
            $marié = strtolower(trim($request->request->getString("marié")));
            if (!in_array($marié, ["oui", "non"], true)) {
                $état += 4;
                $erreurs[] = "valeur [$marié] invalide pour le paramètre [marié]";
            }
        }
        // nombre d'enfants et salaire annuel : des entiers >= 0
        $valeurs = [];
        foreach (["enfants" => [8, 9], "salaire" => [16, 17]] as $paramètre => [$manquant, $invalide]) {
            if (!$request->request->has($paramètre)) {
                $état += $manquant;
                $erreurs[] = "paramètre [$paramètre] manquant";
                continue;
            }
            $valeur = trim($request->request->getString($paramètre));
            if (preg_match('/^\d+$/', $valeur) !== 1) {
                $état += $invalide;
                $erreurs[] = "valeur [$valeur] invalide pour le paramètre [$paramètre]";
            } else {
                $valeurs[$paramètre] = (int) $valeur;
            }
        }
        // erreurs ?
        if ($erreurs !== []) {
            return new ControllerResult(Response::HTTP_BAD_REQUEST, $état, $erreurs);
        }
        [$enfants, $salaire] = [$valeurs["enfants"], $valeurs["salaire"]];

        // on a des paramètres valides - la mémoire de portée [application] : un serveur Redis
        try {
            $redis = new RedisClient($config["redis"]);
            // on se connecte tout de suite au serveur pour savoir s'il est là
            $redis->connect();
        } catch (PredisException $ex) {
            // erreur 500
            return new ControllerResult(
                Response::HTTP_INTERNAL_SERVER_ERROR,
                350,
                "[redis], " . self::utf8($ex->getMessage())
            );
        }
        // création de la couche [dao]
        try {
            $json = $redis->get("taxAdminData");
            if ($json === null) {
                // les données fiscales sont prises dans la base de données puis mises dans Redis
                $dao = new ServerDaoWithRedis(ROOT_DIRECTORY . "/" . $config["databaseFilename"]);
                $redis->set("taxAdminData", (string) $dao->getTaxAdminData());
            } else {
                // les données fiscales sont prises dans Redis
                $taxAdminData = TaxAdminData::fromArray(json_decode($json, true, flags: JSON_THROW_ON_ERROR));
                $dao = new ServerDaoWithRedis($taxAdminData);
            }
        } catch (ExceptionImpots $ex) {
            // erreur 500
            return new ControllerResult(Response::HTTP_INTERNAL_SERVER_ERROR, 341, self::utf8($ex->getMessage()));
        } finally {
            // on n'a plus besoin du serveur Redis
            $redis->disconnect();
        }
        // création de la couche [métier] et calcul de l'impôt
        $résultat = (new ServerMetier($dao))->calculerImpot($marié, $enfants, $salaire);
        // la simulation : les clés du tableau [$résultat] deviennent des arguments nommés
        $simulation = new Simulation($marié, $enfants, $salaire, ...$résultat);
        // on l'ajoute à la liste des simulations de la session
        $session->set("simulations", [...$session->get("simulations", []), $simulation]);
        // réussite
        return new ControllerResult(Response::HTTP_OK, 300, $simulation);
    }

    // (Windows-1252 sous Windows) : il ne pourrait alors pas être mis dans une chaîne JSON
    private static function utf8(string $message): string
    {
        return mb_check_encoding($message, "UTF-8") ? $message : mb_convert_encoding($message, "UTF-8", "Windows-1252");
    }

    {
        // on doit avoir un GET avec les seuls paramètres [action, numéro] dans l'URL

        $session->set("simulations", $simulations);

        return new ControllerResult(Response::HTTP_OK, 600, $simulations);

    #[\Override]
    public function send(
        Request $request,
        Session $session,
        array $config,
        int $statusCode,
        array $content,
        array $headers = [],
        ?Logger $logger = null

        // si aucune vue ne convient, c'est une erreur inattendue : on affiche la vue des erreurs

            $config["vues"],
            fn(array $états): bool => in_array($état, $états, true)
        ) ?? $config["vue-erreurs"];
        // on exécute la vue : ce qu'elle écrit est mis dans un tampon au lieu d'être envoyé au client
        // la vue a accès aux variables [$request, $session, $config, $content] de la méthode
        ob_start();
        require __DIR__ . "/../Views/$vue";
        // on récupère le contenu du tampon, le document HTML, et on vide le tampon
        $html = ob_get_clean();
        // envoi de la réponse par la classe parent
        $this->sendResponse($statusCode, $html, "text/html", $headers);
        // log en JSON de la réponse du contrôleur, sans le HTML
        $this->log($logger, $content);
    }

    23.13.5. The view of unexpected errors

    Here we call an unexpected error an error that should not have occurred during normal use of the web application. Let us take as an example the following request, in a JSON session:

    1
2
    > curl -c cookies.txt -b cookies.txt "http://localhost/php8-oct-2026/scripts-web/impots/version-12/main.php?action=calculer-impot" -d "salaire=y"
{"action":"calculer-impot","état":337,"réponse":["paramètre [marié] manquant","paramètre [enfants] manquant","valeur [y] invalide pour le paramètre [salaire]"]}

    The [marié] and [enfants] parameters are missing, the [salaire] parameter is invalid. Yet in the HTML form of the web application, this case cannot occur:

    • all the parameters are present;
    • the [marié] parameter, which takes its value from the [value] attributes of two radio buttons, necessarily has one of the values [oui] or [non];
    • with a recent browser, the attributes [<input type="number" min="0" step="1" …>] ensure that the inputs for the children and the salary are necessarily integers >= 0.

    However, nothing prevents a user from sending such a request to our server in an HTML session, with [curl] or with their browser's developer tools. We will call an unexpected error an error that should not occur within the HTML application. If it does occur, someone is probably trying to "hack" the application. For teaching purposes, we have decided to display an error view in these cases. In reality, we could redisplay the last page sent to the client. To do so, it is enough to record in the session the last HTML response sent. In the event of an unexpected error, we send this response again. The user will thus have the impression that the server does not respond to their errors since the displayed page does not change.

    // rend l'élément [réponse] de la réponse JSON {"action": ..., "état": ..., "réponse": ...}
    private function getResponse(ResponseInterface $response): mixed
    {
        try {
            // le statut, les entêtes et le document JSON de la réponse, même en cas d'erreur (paramètre false)
            $statusCode = $response->getStatusCode();
            $headers = $response->getHeaders(false);
            $json = $response->getContent(false);
        } catch (TransportExceptionInterface $ex) {
            // le serveur n'a pu être joint
            throw new ExceptionImpots("Erreur de communication avec le serveur ({$ex->getMessage()})", 40, $ex);
        }
        // logs
        if ($this->verbose) {
            print "$json\n";
        }
        // le cookie de session : on garde le dernier envoyé par le serveur
        // (l'action [fin-session] supprime l'ancien cookie et en envoie un nouveau)
        foreach ($headers["set-cookie"] ?? [] as $cookie) {
            if (preg_match('/^PHPSESSID=([^;]+)/', $cookie, $champs) === 1) {
                $this->sessionCookie = "PHPSESSID=$champs[1]";
            }
        }
        // décodage de la réponse JSON
        try {
            $array = json_decode($json, true, flags: JSON_THROW_ON_ERROR);
        } catch (\JsonException) {
            $array = null;
        }
        if (!is_array($array) || !array_key_exists("réponse", $array)) {
            throw new ExceptionImpots("Réponse du serveur invalide [$json]", 41);
        }
        // erreur ?
        if ($statusCode !== 200) {
            // le message de l'exception est la réponse du serveur complétée par son statut HTTP
            $message = json_encode(
                ["statut HTTP" => $statusCode] + $array,
                JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES | JSON_THROW_ON_ERROR
            );
            throw new ExceptionImpots($message, 42);
        }
        // on rend l'élément utile de la réponse
        return $array["réponse"];
    }
